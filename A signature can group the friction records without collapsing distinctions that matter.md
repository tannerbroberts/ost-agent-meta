#Assumption #unvalidated #evidence/assertion

**The belief, stated so it can be false.** A signature computable from a friction event — tool name plus error class — groups the records an operator would call the same event and separates the ones they would call different.

It is false in whichever direction the signature is wrong. Too coarse: every `tool_error` on `Glob` becomes one record, and a permission denial gets merged with an `InputValidationError` about an unexpected `limit` parameter — two different problems, one of them a product defect and one of them a grant that was never given. Both appear in this node's own source session. Too fine: session ids, timestamps or message text leak into the key and nothing groups at all, which is where the adapter already is.

**Category:** feasibility.

**Why this is the belief and not the volume claim.** That roll-up shrinks the queue is arithmetic. What is genuinely unknown is whether the grouping preserves what a reader needed, and this is a claim about a function nobody has written yet, tested against a corpus of eighty-five real records that already exists to test it against.

**The honest caveat about who judges.** Whether a merge collapsed something that mattered is ultimately a person's reading. What a spec can pin is the sharp end: two events an operator has already said are different must not land in one group. That is falsifiable and it is where a signature function fails first.
