#Opportunity #unvalidated #evidence/observed
[[Preflight the run's tool demands against its grant and stop at turn one]]
[[The run's report leads with what it was refused, so a denied night cannot read as a quiet one]]
[[Derive the permission allowlist from the skill's own allowed-tools, so the two lists cannot drift]]

I set a run going while I am asleep, and it spends the night being told no.

The instructions the run is given name tools. The grant it is handed does not include them. Nothing compares the two before the run starts, so the mismatch surfaces as a denial in the middle of work — after the run has already decided what it was going to do, and against a person who is not there to say yes.

Two things are wrong with this and only one of them is the missing permission. The other is that a denial to an unattended run is indistinguishable, from where I sit the next morning, from work that simply was not needed. The run reports what it did; it does not report the shape of what it was stopped from doing. So a night of denials reads as a quiet night.

What I want is to know before I walk away that the run can do the job I set it, and to be told plainly if it could not.

**The sharpest form of the cost is a denied write, not a denied read.** A denied read costs turns and has a workaround. When `ost_flag_humans_required` was denied, three assumption tests that name outside people as the measurement could not be labelled, and the finding was written into their `## Issues` prose instead — where nothing that reads the `lane:` field will ever see it. A reader checking lanes mechanically still sees three unlabelled tests that look runnable, and the pass that recorded it looks, from its own summary, like it handled the item. The same shape applies to `ost_check`: a pass that cannot run the invariants makes forty writes and then reports its own correctness on a gate it was not allowed to open.

## Finding 1 — the tool-class gap was a decision, not an oversight

Every early pass inferred from the stable denied set that there was "a fixed, enumerable list nobody has applied to the allowlist", which reads as an instruction to apply it. Reading the product repo says applying it would have overwritten a decision. `src/knowledge/ruleset.ts` withholds exactly these tools from the unattended pass on purpose, in terms: a skill grant "does not move a single cell of that table" and must not "drift into the unattended sweep by association." The reasons are per-tool and recorded in `test/release/examples-allowlist.test.ts` (`CONTAINED_ON_PURPOSE`) — `ost_flag_humans_required` is R7's containment, `ost_check` was judged exposition rather than a step, `ost_rank_source` keeps source-finding and source-promoting out of one agent's hands. **The skill declares 22 tools, the surface grants 16, and the difference is deliberate.**

So the defect sits one layer over from where this node originally put it. It is not that the grant is too narrow. It is that the pass is handed the *declaration* as its system prompt and never told which part of it does not apply here — and under `-p` a tool outside the grant is denied with no message, so there is no way to learn it except by spending a call.

Shipped as OST-Agent PR #69: `autonomous-pass.sh` derives the withheld set from the two lists it already holds and names it in the system prompt, stating that writes are unverified *by design*. It renders nothing when the lists agree, so retiring a containment removes the section rather than leaving a stale copy. The grant is untouched.

**A second finding from the same reading, worth more than its instance.** Both loops printed `Permission deny rule "SlashCommand" matches no known tool` on every firing for four days. Claude Code had renamed `SlashCommand` to `Skill`; an inert deny rule provides no coverage, so the delegation capability that deny list exists to refuse was reachable from an unattended pass the whole time. Fixed in the same PR. **A guard that names something which no longer exists reads exactly like a guard that works**, and the only signal was a warning line that looked like noise.

## Finding 2 — the fix held for a week, broke once, and has held since

Zero withheld-tool denials were recorded by the passes of 2026-08-07, -09, -10 and -16, each of which confirmed first-party that the "What this surface withholds" section was present in its own opening context. Two of those passes had a live occasion — they reached work that genuinely wanted `ost_flag_humans_required`, the single most-denied tool in the corpus, and did not call it.

**The streak broke on 2026-08-17 and the break went unnoticed for four days.** `TRANSCRIPT:90d8aeae-192e-4adf-9dd5-746832e3753e` is an unattended firing whose entire friction content is **eight consecutive denied calls to `ost_flag_humans_required`**, plus two retries — not a mixed session with one slip, but eight identical calls with nothing attempted in between. 83 + 8 = 91 and 28 + 1 = 29, so the arithmetic closes exactly and that one session is the entire regression. Eight is eight times the pre-committed bar, making it the first recorded failure of the mechanism. The 08-22, 08-28 and 08-29 recounts all show the class flat at 91/29 — a fourth consecutive identical reading, now spanning twelve days and 78 transcript records added since 08-22 with no new occurrence — so the failure was isolated rather than the start of a decay.

**The question this node cannot answer, and will not guess.** Whether that firing's opening context carried the withholding section at all. A pass can read its own prompt and no other, and nothing in the vault records what prompt any other firing was handed. The two live readings — the section was absent (sound mechanism, broken wiring) or present and disregarded eight times (mechanism refuted) — **have opposite remedies.** A human with the loop's invocation log for 2026-08-17T07:16Z can settle it in one look; nobody else can.

**What outlives whichever answer wins.** The bar existed, the measurement was mechanical, and the failing record was captured within the hour — yet this node still read "streak holds" for four days, because a census here is prose a pass writes by hand when it happens to recount. That is a separate need and has its own node, "A measured bar is only re-taken when a pass feels like it, so a fix reads as working long after it stopped".

## Finding 3 — the path-read class is the larger half, and was triaged behind the smaller one

By volume the tool class always looked like the whole problem. By reach it is the other way round: the path class appears in 105 sessions to the tool class's 29, and it is the only one still growing (36 → 50 → 69 → 75 → 98 → 105 sessions). It was invisible for months because it costs about one call per session instead of three, so it never surfaced in a tally sorted by volume — a run hits a directory denial once, concludes the path is unavailable, and stops. That is the *absence* of this node's title behaviour, which is exactly why it never produced the signature that got attention.

**The 08-29 reading reverses the acceleration the 08-28 reading reported, and the reversal is a lesson about the metric rather than about the defect.** The 08-28 pass called its row "the steepest rise in the series" — 23 new sessions in six days — and read the two classes as visibly diverging. That comparison comfortably beat the tool class's zero, but it was never normalised against the denominator, which was growing at the same time. Normalised, the picture inverts: of the 36 records added between 08-22 and 08-28, 23 carried a path denial (**64%**); of the 42 added between 08-28 and 08-29, 7 did (**17%**). The cumulative share barely moved across the same window — 18.8% at 08-22, 22.5% at 08-28, 22.0% at 08-29 — so the "steepest rise" was mostly more records, not a higher rate. **A cumulative count over a growing corpus rises whether or not anything is getting worse**, and this series read that rise as acceleration for one full pass. The marginal rate is the figure that answers the question this node is actually asking, and on its first two readings it fell roughly four-fold. Two marginal points are not a trend and one of them spans a single day, so this is a correction to an over-read rather than a claim that the class is improving.

**What stays true regardless.** The class received no code fix — its only intervention was a config edit that Finding 3's correction below shows was aimed at the wrong lever — while the tool class received PR #69 and went flat and has stayed flat across four readings. That contrast is still the useful one, and it still points at where the remaining spend is.

**Correction to the record, and it makes the claim narrower and harder.** Passes through 2026-08-10 called this "one line of `product.repos` config, unapplied". `ost.config.yaml` in fact sets `product.repos: [/Users/tanner/dev/OST-Agent]`, dated by its own comment to 2026-08-09. The configuration gap is closed. The continuing denials are raw `Glob`/`Read` calls against the product directory made by whatever surface a firing runs on — **a harness sandbox permission this product's config cannot reach.** `product.repos` was never the lever, which is why the path bar above is unmet, unowned, and moving the wrong way.

**The two grants are separable, and this is now the observed default rather than an intermittent effect.** `Glob` on `/Users/tanner/dev/OST-Agent` is denied while `ost_read_repo` answers normally against that same directory, observed within single sessions rather than inferred across firings (2026-08-22, and again in `TRANSCRIPT:694ffe89-2427-4fd2-bb14-f736c079698b` seventeen minutes earlier). A pass that reaches for `ost_read_repo` first loses nothing but the calls it spends finding out.

**Confirmed again first-party on 2026-08-28, and the way it was nearly missed is the part worth keeping.** That firing had `Glob` and `Read` denied on the product path and `ost_read_repo` answering normally against the same directory — the separable-grants default, third independent observation. It nearly did not find out: its run prompt stated as a hard rule that outward sensing including `ost_read_repo` was withheld from the unattended surface, while the skill's own authoritative withheld list (the one citing `CONTAINED_ON_PURPOSE`) did not name that tool at all. The pass believed the prompt, wrote off 64 uninstrumented solutions as unreachable, and only tested the tool because the two statements disagreed. **A prose claim that a tool is unavailable costs more than a denial does** — a denial is one wasted call, whereas being told in advance suppresses the call entirely and there is no record that anything was skipped. Whoever owns the run prompt should reconcile it with the withheld list; until then the cheap move is to spend the one call and find out.

## Standing caveats on every zero-denial reading above

Four, and they compound. The observer is the subject, so this is an agent reporting its own compliance. Each reporting pass had read the bar it was being measured against before it acted, which is the sharpest form of that problem. A pass that makes no denied call is not distinguishable from the outside from a pass that had no occasion to make one — weakened but not removed by the two passes that did have an occasion. And each firing's own denials are absent from its own census, because a session's transcript is filed after it ends, so every path-class count is a floor by one session in a known direction.

**Nothing available to an unattended pass can separate "the preflight works" from "the preflight works on a run that has been told about the preflight."** That needs a firing never handed the section, which is a human's experiment to arrange. This node should stop trying.
