[[A pull adapter per source the pass reads directly, on its own schedule]]
[[The source pushes to a receiving endpoint that writes straight into the inbox]]

**The need (customer's voice):** "I want the OST-Agent to be able to pull data from experiments directly instead of waiting for it to land in an inbox." (Founder, verbatim, 2026-07-25.)

**Why it matters:** Today the inbox is the only door into the tree — every piece of evidence, including the results of the tree's own assumption tests, waits at its source until a human (or a session acting for one) hand-carries it in. That makes evidence latency a function of operator attention, which is exactly the scarce resource the product exists to conserve. An assumption test whose result is sitting in an analytics dashboard is, from the tree's point of view, still unrun.

**The implied prerequisite (recorded, may deserve its own node):** For the agent to fetch experiment data at the source, it must hold a model of the product being discovered — its edges/surfaces, what instrumentation exists on each, where the data each experiment produces actually lands. The founder stated this implication directly: "the agent should know about the edges that define the product, data gathered on it, etc." No such product-model artifact exists in the vault today; the closest thing is each test's prose description of its own threshold.

**Relation to neighbors (why this is not a duplicate):** [[Fresh outside findings never reach the tree unless I go get them]] (added the same day by a concurrent session) is the same *shape* — evidence only arrives if hand-carried — but a different *source domain*: that node is about outside-world signal (web research, competitor moves, public complaints); this one is about the operator's own product — experiment results already being generated by instrumentation the operator controls, plus the product-model the agent would need to find them. [[Connecting my systems of record could leak or corrupt them]] is the *fear* that gates connecting sources — this node is the *capability* the fear gates. [[I want my usage to automatically feed into and make the OST-Agent better]] is the agent's own tool-trace — this node is about the operator's product data. [[Real-world signal gates outcome achievement]] is a solution that presupposes exactly this capability without naming it as a need.

**Litmus test:** More than one way — read-only source adapters polled at pass time, webhooks/push from experiment platforms, agent-run queries against a local mirror (see [[Local read-only mirror of source systems]]), an MCP connection to the analytics stack, a product-surface manifest the agent maintains and walks. Distinct approaches with real trade-offs. Passes.

**Placement:** Top-level under the Outcome — it is an evidence-channel need parallel to the inbox itself, not a child of the connection-fear node (which constrains *how*, not *whether*).
