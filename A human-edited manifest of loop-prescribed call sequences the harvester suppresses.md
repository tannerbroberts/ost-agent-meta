#Solution #unvalidated #evidence/assertion
[[The founder will keep a manifest of prescribed call sequences current as the loop's steps change]]

**Variation dimension: automated-vs-manual. Position taken: the matching is automated, the definition of "procedure" is deliberately left manual.**

A small declarative manifest lists the call sequences that are procedure rather than pain — `ost_ingest_inbox` followed by `ost_next_work` at the close of a pass; a blocking `TaskOutput` on a task the same session started. The harvester matches every candidate friction event against it and suppresses the matches automatically, with no judgement at harvest time. What stays manual is the list itself: a person edits it, because what counts as prescribed is set by the ruleset the person writes, and the ruleset changes.

**Why the manual half is the point, not a shortcut.** The loop's procedure is not a property of the code — it lives in the skill text and the firing prompt, both of which a human rewrites. Any mechanism that infers "prescribed" from the code would be reading the wrong artifact and would go silently stale the next time the loop's steps change. Making the list an artifact a person edits keeps it in the same place as the thing it describes, and a manifest entry that no longer matches anything is visible in a way an inference is not.

**Against the siblings.** Unlike deleting the `retry` class, this keeps genuine retry-after-failure signal intact — a repeat that is not on the list still files. Unlike adopting the host's error flag, the suppression rule is authored here and can encode this product's own procedure, which no upstream signal knows anything about.

**What it costs.** A maintenance burden with a known failure mode: this project's own tree already records that artifacts asking for recurring founder input are the ones that go unmaintained, and there is a live assumption elsewhere on exactly that question ("The founder will actually maintain a highlight criteria note over time"). A stale manifest fails in the dangerous direction — it keeps suppressing a sequence that has stopped being procedure, so real friction goes missing rather than merely unfiltered.

**What would make this the wrong pick.** If the prescribed sequences turn out to be few and stable, a manifest is ceremony around two hard-coded rules. If they turn out to be many and fast-changing, nobody will keep it current. It is the right pick only in the middle case.

Unvalidated — a human to review.

## Standing finding: the generator, read off the code

Established 2026-08-28 and confirmed by every sweep since. This node was ideated from the theory that the harvester counts prescribed procedure as friction. It is no longer theory — the mechanism has been read first-party out of `src/adapters/transcript.ts` and observed firing on record after record.

**The mechanism.** `extractFriction` builds a signature as `` `${name}:${JSON.stringify(input)}` ``, keeps a `seenCalls` set, and pushes a `retry` on the second appearance of a signature — with no reference to any `tool_result`, `is_error`, or outcome of the first call. `ost_ingest_inbox` and `ost_next_work` both take no arguments, so every call either makes has the identical signature `{}`. The unattended loop's own prompt prescribes calling both at step 1 and re-calling both at step 5. The second pair is therefore guaranteed to trip the repeat detector: the procedure the firing was instructed to follow is the generator.

**And a clean run does not stay silent.** `TranscriptSource.fetchSince` contains `if (events.length === 0) continue`, so a session with no friction produces no evidence item at all. A firing that followed its instructions and hit nothing wrong therefore does not produce nothing — it files a document titled "Session friction" whose entire contents are the loop obeying itself. Pure instances observed: `6d96802b` (2 events), `ec918ca1` (5), `29ee50b7` (2), `01e55025` (2), `0e24ead9` (2), `0ffc6652` (1), `030e5db3` (5 retries, the highest retry count in the 2026-08-30 sample, every one prescribed).

**The detector is wrong in both directions, which bounds any rule built here.**

- *False positives — procedure read as friction.* The case above. Suppressible, and the no-argument condition is what makes it safely suppressible.
- *False negatives — real repeats the detector never sees.* `TRANSCRIPT:60eba32c` is 9 events, all `tool_error`, **zero retries**, six of them `await: gave up after 300s`. Since `seenCalls` spans every `tool_use` block and ignores outcomes, zero retries means no two calls shared an input: the session asked one question — has the suite finished yet — six times over 1800s and registered as a repeat exactly zero times, because the caller incremented its output filename between attempts. Detector recall on that record is 0 of 6. The consequence for that branch is recorded on "A repeated wait on the same condition resumes and doubles its budget automatically, up to a ceiling set once by hand".
- *Must-not-suppress — argument-carrying repeats that are genuine signal.* `cf2cef94` (2 retries, both re-issues of a wait that had just expired, from which a pass distilled a new Opportunity) and `09ec7cd2` (a `retry` on `Write` with a full argument payload, a real repeat of a write to the build loop's report file). Any rule must suppress the no-argument prescribed pair without taking these with it. That distinction is pinned by the sibling test "A repeated no-argument call with no error files nothing, while a repeat whose result is an error still files".

## Standing census: what the corpus is made of

Three counts were taken across passes at widening scope. Where they disagree, the widest supersedes; the narrower ones are kept because they say how the figure was arrived at.

**Whole-record self-manufactured noise — 76 of 534 (14.2%), full corpus, 2026-08-31.** Counted over every transcript record on disk via `Glob`/`Grep` on `.ost-agent/evidence/`, from each record's own header parenthetical: 78 of 534 carry no `tool_error` at all, of which exactly 2 (`da806545`, `414d3daa`) carry an argument-bearing retry and are therefore genuine. *Superseded estimate, kept for method:* a 2026-08-30 count over the 25 records the sweep showed put it at 3 of 25 (12%), and named its own limit — the 25 are the unfiltered head ordered by id, not a random sample. The head turned out to represent the tail.

**Must-not-suppress class — at least 197 of 534 (36.9%).** Records carrying at least one argument-bearing retry. This is a **floor, not a measurement**: it counts records where the detector fired, and the `60eba32c` finding above shows a semantic repeat with a varying argument is invisible to it. The direction of that error is the safe one for this candidate — an invisible repeat never becomes a `retry` event, so a rule scoped to the no-argument condition cannot take one with it. It is not safe for any future work that reads the retry class as a measure of how often the agent repeats itself.

**What suppression would actually buy, and it is not queue length.** 534 records become ~458. The queue is not long because of self-manufactured records. What suppression buys is signal-to-noise *within* a record: a reader stops seeing two lines of the loop obeying itself under every real finding. That is a real improvement and a much smaller one than "the backlog grows fastest when nothing is wrong" implies.

**Why the queue is actually long — a third mechanism, distinct from this node's subject.** A 2026-08-30 section concluded that 88% of records carry genuine `tool_error`s "that no Opportunity has ever been distilled from… That is discovery debt." That reading was wrong, and a 2026-08-31 pass corrected it by opening 7 records in full (`134bad7e`, `1329bda4`, `1eed544a`, `10002eba`, `0e0cd6f3`, `132bb394`, `6e1984b2`) and tracing all 26 `tool_error` events to nodes: **22 of 26 (85%) carry a signature the tree has already mapped and counted** — `File has not been read yet` alone is 13 of 26, censused corpus-wide at 416 events across 221 sessions on "The file changed after I read it, and the failed edit is how I find out"; plus `No such file or directory` (63 corpus-wide), `InputValidationError` on Read (46), Monitor's multi-operation approval refusal (8). Four were singletons this pass could not trace. **New needs distilled from all 7: zero.** So the queue is mostly *records whose signature is already mapped, which are never retired once mapped* — a mechanism distinct from both the noise this node is about and the debt that section inferred.

**Forward checks, not just retrospective ones.** Four consecutive firings have scored their own arrivals before doing anything else, and every one found zero new needs: 3 arrivals / 12 events (2026-08-31), and this firing's 2 arrivals / 9 events (2026-09-03) — `62543b0f` (7 events: three `await` expiries, two read-before-write errors, one Edit old_string mismatch, one prescribed retry) and `ea237dc4` (a `Glob` permission denial on the product repo plus the prescribed retry). Every signature in both was one this tree already holds.

**One class of arrival is avoidable and no earlier note said so.** The `Glob` denial on `/Users/tanner/dev/OST-Agent` regenerates once per firing — `79b70e58` was a record of a prior firing's denial, filed by a firing that then hit the identical denial itself, and `ea237dc4` above is the same thing again. It is not a missing capability: `ost_read_repo` reads that repository fine and was used to list `test/` and read `src/adapters/transcript.ts` on several passes including this one. What `ost_read_repo` cannot do is *search*, which is a real gap. So a firing reaching for `Glob`/`Grep` to **list or read** the product repo is burning a call and minting an unretirable record for something it already has; a firing reaching for it to **search** is hitting a genuine limit. Both produce the same friction line, so the corpus cannot tell an avoidable denial from a blocking one — and only the second kind is evidence of anything.

**The age-out knob misses this node's failure case by construction, and the caveat on that claim is discharged.** `evidence.ageOutDays` is unset on this vault, which is why `agedOutEvidence` reads `{count: 0, oldest: null}`. The implemented rule is age **AND** redundancy with a signature some node has already cited — "AGE ALONE MAY NEVER COLLAPSE AN ITEM", in the words of `test/evidence/age-out-preserves-novel.test.ts`, which builds a fixture so that pure age fails it. The self-manufactured records have no cited signature to be redundant with, precisely because there is no genuine need underneath them to distil, so enabling the knob would leave exactly these records listed forever. A 2026-08-31 pass flagged that this rested on a spec description rather than a first-party read of the live path; a later firing the same day closed it by confirming that spec drives `computeNextWork` from `src/mcp/next-work.js`, the production sweep entry point, with the knob as its sixth argument. A separate module, `src/ost/ageing.ts`, implements a *different* rule (N untouched passes, reset by a changed signature) and is replay-only, so it cannot be used to preview what the knob would bury. Both halves stand together: the knob misses this candidate's 14.2%, and is aimed squarely at the 85% already-mapped bulk that this candidate does not touch.

**Method and limits, for the whole census.** Counts are per-record, not per-event, so nothing above describes the event mix inside the 197. The retry-only set was identified from header parentheticals rather than by parsing each event list, so a malformed header would be miscounted. The claim that no-argument retries are only ever `ost_ingest_inbox`/`ost_next_work` rests on a 40-line sample. The signature-to-node tracing was done by reading node bodies rather than by grep, so a mapped signature could have been missed and counted as a singleton — an error that runs towards *understating* how much of the queue is already mapped. 534 is every transcript record on disk and is a larger denominator than the unmapped count the sweep reports; the two answer different questions and should not be differenced.
