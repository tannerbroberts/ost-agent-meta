#AssumptionTest #unvalidated #evidence/assertion

**Risk category: feasibility. Small and fast: it reads two artefacts already in the repository and compares them.**

Take every command-shaped example quoted in an `ost_*` tool description and run it through `parseInstrument` from `src/knowledge/instruments.ts`. Each must come back as an instrument rather than a rejection. Then seed the mismatch deliberately — a description quoting a form the validator does not accept, such as one carrying a `-t` filter — and assert the check fails on it, so the parity test cannot pass vacuously.

The positive control is the part worth insisting on. A parity check that finds nothing looks identical to one with nothing to find, and this vault has already been bitten by that shape: `test/ost/vault-write-guard.test.ts` carries an explicit "the guard cannot pass vacuously" block for the same reason, and the `no-spec` classification exists because a red that every question would produce distinguishes none of them.

**Why it is red today.** No such check exists — nothing in the suite reads a tool description at all, so no artefact today asserts the two agree. It goes green when the parity check is written and the descriptions are made to satisfy it.

**Honest labelling of how red it is.** `test/mcp/description-grammar-parity.test.ts` does not exist, so the first run is filed `no-spec` rather than a true red, and would fail identically for any question written on that path. `test/mcp/` is a real, populated directory, and the threshold above is a bound bar with a positive control in it — the two properties this vault's own 2026-08-09 and 2026-08-21 findings identify as what separates a weak red a builder can act on from one they cannot. The stronger form, naming an assertion inside an existing spec, is not expressible: the instrument grammar accepts a bare `npx vitest run <path>.test.ts` and rejects a `-t` filter as shell punctuation.

**A note on what this test is an instance of.** The candidate it serves proposes publishing a grammar; this test's own instrument was constrained by that same grammar being unpublished and discovered by refusal. That is not irony worth much, but it is one more first-party sighting of the refusal class the parent opportunity is about, and it happened during the pass that wrote this node.

**What a green does not settle.** Whether publishing the grammar stops the refusal — that depends on a session reading the description before composing, which is a usability question about the reader and needs a separate test. It also covers only grammars statable in advance, so it says nothing about the state-dependent refusals (the humans-required lane) that this candidate admits it cannot reach.

## 2026-09-09 — the grammar is read first-party at last, and it makes `no-spec` a proof rather than a habit

Kept short. This is not a reproduction of anything; it closes the limit the section above states in its own last paragraph.

**What was read.** `src/knowledge/instruments.ts`, 5,728 bytes, `wouldTruncate: false`, whole and untruncated via `ost_read_repo`. This node's body has named this module as the home of `parseInstrument` since it was written, and no pass had opened it — the three earlier attempts all reached for `src/ost/instrument.ts` (29,758 bytes, `wouldTruncate: true`), could not be served it, and took the refusal rule from the tool description plus an observed refusal string instead. That inference is now replaced by the source.

**The grammar, recorded verbatim so nobody reads it again.** `INSTRUMENT_FORMS` holds exactly one entry, `vitest-spec`, whose pattern is `^npx vitest run (?<target>[A-Za-z0-9][A-Za-z0-9._/-]*\.test\.ts)$` and whose argv is `["vitest", "run", target]`. Two checks sit around it: a pre-check `SHELL_METACHARACTERS = /[;&|` + "`" + `$(){}<>\\\n\r*?!#~'"]/` applied to the whole string before any form is tried, and a traversal check rejecting a target that starts with `/` or contains a `..` segment.

**So the `-t` form is refused twice over, and that is now established from the parser rather than from the error text.** The double quotes in `-t "…"` are in the metacharacter class, so the string is rejected before any form is consulted; and even written unquoted it would fail the pattern, which is anchored with `$` immediately after `.test.ts` and admits no trailing argument. Finding 2 of the section above is confirmed at the source.

**The consequence is a proof, not an observation, and it is the builder-useful part.** An instrument must satisfy two conditions at once: match that single form, which permits one spec path and nothing else; and fail against the repository today, since an instrument already green is refused rather than recorded. Against a suite that passes, the only string meeting both is a path that does not exist — which is exactly the `no-spec` classification. The rollup's count of 260 of 266 recorded reds reading "No test files found" is therefore not 260 authors taking the cheap route; it is the only instrument the tool will accept. The pass prompt's own worked contrast asks for an assertion-level `-t` filter against an existing spec and calls the missing-file form weak. That stronger form is unrepresentable by construction, so an unattended pass instructed to prefer it can only either compose a refused call or write the form it has just been told is worthless.

**What this does not settle, and it is the whole question.** Whether the grammar should be widened. The module's own doc comment argues the closed vocabulary IS the anti-fabrication guarantee — "an agent that could write any shell string could write one that exits 0 and hand itself a passing test — the tree's credibility spent on `true`" — and states that adding a form "is a real decision: it widens what an unattended pass can put its name to." A `-t` filter is not a shell string and does not obviously breach that bar, since the verdict still comes from committed code and the argv layer never reaches a shell. But that is an argument, and choosing between a narrower grammar with weaker reds and a wider one with stronger reds is a trade between two goods rather than a defect to repair. It is a human's call, and this pass does not make it.

**Bearing on this node specifically, which is to widen it further than its own last section did.** The threshold reads "every example command quoted in a tool description parses". With the parser in hand that is now mechanically checkable, and the scope extension the section above proposes — to `.claude/commands/ost-pass.md` and `src/knowledge/ruleset.ts` — is confirmed necessary rather than suspected: the pass prompt's `-t` example is a command-shaped example that provably does not parse, so a parity check reading only `ost_*` tool descriptions passes while the specimen that motivated this node stands untouched.

**Limits.** This is the grammar module, not the runner. The rule that an already-green instrument is refused is taken from this module's doc comment describing `src/ost/instrument.ts`, which still cannot be served whole, so it is second-hand here as it was before. The metacharacter class is transcribed from source and should be re-read rather than trusted if anyone depends on a specific character.
