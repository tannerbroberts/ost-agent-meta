**The need.** When I decide that a question can only be answered by a person, I want that decision to be recorded as a decision — not to reappear on every future pass as an outstanding failure to write a command. Today the opposite happens: the deliberate answer and the un-done work are indistinguishable in the queue, so every firing pays to re-derive a conclusion the tree already reached, and each one arrives at a node whose prose is arguing with the counter that summoned it.

**Litmus test (more than one way to address this?):** Yes, and the candidates disagree about who should act. Filter the bucket in code so the listing never mentions them. Route them to `outstandingAsks`, which already exists and already ages a pending ask, so the work is re-labelled rather than hidden. Or copy `trustsShippedStatus` exactly and exclude only on a lane a human's `ost-agent lane --set` recorded in History, distrusting the bare frontmatter field. Passes.

**What this node does not claim.** It does not say every bucket entry is of one kind. It does not say `humans-required` is the correct lane for any particular one — several entries argue their own case and a reader may disagree. And it says nothing about desirability: this is observed behaviour of the product, read from its own source and its own sweep output, which grounds usability and is not evidence that anybody outside this project wants it fixed. Rung `assertion` — a claim from inside the building. No test has been run on it and no result is recorded.

## Standing finding: the mechanism, read off the source and confirmed twice by arithmetic

**The filter.** `solutionsMissingInstruments` in `src/eval/buildable.ts` (read in full via `ost_read_repo`) clears a Solution from the bucket on exactly three conditions: `status === "deferred"`, `trustsShippedStatus(n)`, and any test beneath it carrying a parseable instrument. **There is no lane check.** Two functions below it in the same file, `testsAwaitingVerification` does have one — `if (n.lane === CAUTIOUS_LANE) continue;` — with a comment explaining why: "A test a human put beyond compute's reach is never run by compute." `CAUTIOUS_LANE` is `humans-required` and `computeMayRun` returns false for it (`src/knowledge/lanes.ts`). So the codebase already holds the exact predicate that would settle this, applies it to one queue, and does not apply it to the other.

**The consequence, and why it compounds rather than merely annoys.** A Solution whose every assumption test is correctly labelled `humans-required` can never leave this bucket. The only call that could label a test into that lane from an unattended surface is `ost_flag_humans_required`, and it is not granted on `/ost-pass` — pinned in `test/eval/clearability.test.ts`, whose `lane-conflict` row records the reason as "on `/ost-pass` the tool is not granted at all (R7's containment)". So the sweep is handed a bucket, told to clear it, and holds neither the tool that would clear it nor an honest command to write instead. The instruction and the grant disagree, and the pass in the middle absorbs the difference.

**The precedent is in the same file.** `solutionsMissingInstruments`' own doc comment records that "Four solutions correctly parked as `shipped` recurred in this list on every pass until each future sweep either re-derived the same conclusion or was tempted to invent a command that could not fail." That is this defect in different clothing, already recognised and already fixed once — for `shipped`, by `trustsShippedStatus`. The humans-required case is the same failure with the same two outcomes, and the second is the dangerous one: a pass that resolves the pressure by inventing a command puts a test into the tree that cannot measure the belief it hangs under.

**Confirmed twice by counter arithmetic, independently of reading the source.** Two firings each created three Solutions in one sitting — two whose tests carry an `instrument:`, one whose test was created with `humansRequired:` — and re-ran the sweep. On 2026-08-30 the bucket moved **68 → 69**; on 2026-09-08 it moved **74 → 75**. Both times exactly the humans-required candidate entered and both instrumented siblings stayed out. The instrumented pair is the control — same author, same pass, same parent — so the difference is the lane and not the writing or the age of the node. The second run matters especially because that pass's own `ost_read_repo` read of `src/eval/buildable.ts` **truncated at the `solutionsMissingInstruments` docstring**, so the source route was unavailable and the arithmetic route reached the same answer without it.

**What the control rules out.** That the bucket is simply full of old nodes written before lanes mattered. A node created under the current rules, with a lane set deliberately at creation, lands in the bucket immediately.

**The trap, and it decides between the three candidates.** A lane reaches a node two ways: a human's CLI call, or `ost_create_node`'s own `humansRequired:` argument, which an agent passes at creation time. A filter that trusts the bare field lets an agent take its own work off the queue by declaring it needs a person — the same self-certification `trustsShippedStatus` was written to refuse. Whichever candidate is chosen has to answer that, and any answer that trusts the bare field is choosing to.

## The one exclusion an agent can write itself, and pulling it would be a lie

Of the three conditions that clear a Solution from this bucket, exactly one is writable from an unattended surface, and it is the bare one. `trustsShippedStatus` was built specifically to refuse self-certification — its doc comment says the exclusion "does not trust the bare field — `status: shipped` is agent-settable — only a promotion recorded in `## History` with reasoning attached leaves the queue." The instrument condition needs a command that fails today. But `deferred` is excluded on the bare field, deliberately and with a stated rationale: "unlike `shipped`, `deferred` makes no claim about code that exists to audit against the repository." And `ost_set_status` offers `deferred` on the unattended surface, ungated.

**So the bucket a pass is told to clear, and cannot clear honestly, has precisely one lever the pass can pull unilaterally — and pulling it is a lie.** `deferred` means abandoned. Every entry every census here has classified is the opposite: waiting on a person, or outside `product.repos`, or already built. A firing under standing instruction to drain the bucket, holding no `ost_flag_humans_required`, could empty it completely with one status call per entry and produce a green sweep in which nothing was decided and every live candidate was retired. Nothing in the code, the ruleset, or this node currently says not to.

The asymmetry is the finding: the codebase distrusts the agent on `shipped`, distrusts it on the instrument, and trusts it on the one status that silently retires a candidate. This node's own trap paragraph says "any answer that trusts the bare field is choosing to" and applies it to the lane; the reasoning transfers exactly to `deferred`, and there it is not a design question for a future candidate — it is shipped behaviour with an agent-writable key. None of the three candidates addresses it, because all three are about adding an exclusion and this is an exclusion that is too easy to satisfy. Whoever builds one should decide separately whether `deferred` deserves the `trustsShippedStatus` treatment, or whether the honest answer is that a bucket with no honest exit should not be a bucket a pass is instructed to clear.

**What the passes that found this lever did with it: nothing.** No status has been changed on any bucket entry by any pass that recorded this. Stated explicitly so a later reader can tell the hole was found and left alone rather than found and used — and because this vault carries a category named "The agent narrows its own capability to get past a gate I set", of which this is an instance with the narrowing available for free.

## What the bucket cannot say at all: the half-instrumented solution

Every census above studies solutions wrongly *in* the bucket. This is the opposite direction and it is not a restatement of the lane argument.

`resolveTestsUnderSolution` walks Solution → *every* Assumption → *every* AssumptionTest beneath each and returns the flat union; `solutionsMissingInstruments` then clears a Solution on `tests.some((t) => nodeInstrument(t.test))`. So **one** instrumented test anywhere under a solution removes it, however many of its other assumptions carry no runnable test at all. A solution resting on four beliefs with one instrumented test is reported as served, identically to one whose four beliefs are all instrumented.

Read against that function's own stated purpose — solutions that "cannot reach a builder, because everything written about it is prose" — `.some()` is the right predicate: one red command is enough for work to start. The gap is that no other surface picks the question up. `src/eval/coverage.ts`, read in full, classifies thresholds and pairs recorded results against `## Uncovered` statements; it never asks whether each assumption beneath a solution has a runnable test. `solutionsMissingAssumptions` counts solutions with no test at all. **Nothing counts the middle.**

Where that becomes a claim rather than an omission: `permitFrom` selects `live[0]` — the first red test it finds — and returns the reason string "`<command>` fails today and passes when `<solution>` is built. **That is the definition of done.**" On a solution resting on four assumptions with one instrumented test that sentence is false in the direction that costs most: a builder turns one command green and the permit reads as spent, while three beliefs were never given a runnable form. This is the failure the Assumption layer was introduced to prevent — `ost_create_node`'s own description says "a solution resting on four beliefs is not covered by one test against one of them — which is the distinction this layer exists to keep." The layer keeps the distinction; the permit that reads the layer discards it.

**The size of the masked population is not established.** The instrument-less tests cannot be mapped onto bucket entries without a per-solution join, and that join is not computable from read-only greps. What the mechanism does establish is that masking occurs whenever an instrument-less test shares a solution with an instrumented one, and that no queue in the codebase would report it if every such test in the vault were of that kind. None of the three candidates would surface it either, because all three operate on entries the bucket already lists. Whether a solution's assumptions should be counted individually, and whether a build permit should say how many of them its one command covers, is a fourth question and a human's.

## The fourth candidate already ships, and it misses this vault

**The prose-declared population.** `proseDeclaredLane(node)` in `src/ost/lanes.ts` returns the lane a test declares in its own prose but not in its frontmatter, and `triageLanes` already surfaces those as `proseDeclared` alongside `laneConflicts` and `proseLaneAmbiguity`. It is not a naive regex, and `test/ost/lanes.test.ts` says so with cases taken from this vault: it ignores the `lane: X → Y` audit line `setLane` writes under `## History`, ignores a lane named in an `## Issues` annotation, refuses a split declaration such as "Lane: compute-only for the census, humans-required for the fixing" by returning it as an ambiguity rather than taking the first match, and drops an unrecognised lane name. It reads AssumptionTests only. Counted whole-tree on 2026-08-31: 494 files carry `type: AssumptionTest`, **127** carry a prose declaration matching `^**Lane: ` (all 127 AssumptionTests, checked by requiring both in one multiline match), 60 carried a frontmatter `lane:`, and exactly **14** carry both — so **113 AssumptionTests declare a lane in prose that their frontmatter does not carry**, and prose declarations outnumber frontmatter labels 127 to 60. A candidate reading the declaration rather than the label therefore has 113 more nodes in reach. But a prose declaration is agent-written, exactly like `humansRequired:`, so a filter trusting it lets an agent take its own work off the queue by writing a sentence: it buys **reach, not authority**, and sits on the same side of the self-certification line as the lane filter.

**The bulk labeller is not a build and not a grant — it already exists.** `test/cli/lanes.test.ts`, read in full, pins **`ost-agent lanes --flag-cautious <by>`**, and it does the fourth candidate's job today with exactly the safety properties this node has been arguing one would need. It labels in bulk (`flagged "Interview five real players"`, writing `lane: humans-required` into frontmatter). **It only ever moves toward a person** — the hint spec asserts `not.toMatch(/⚠ likely compute-only/)`, there is no permissive bulk call, and the comment says why: "the permissive call is a judgement and bulk is the wrong shape for it." **It never reverses a human's permissive call**, pinned by a dedicated test commented as "the one bulk failure that would be a safety regression rather than noise." And it refuses to read as finished: `1 remain unclassified` and `still NOT runnable by compute` are asserted, and an empty run prints `Nothing to flag` and never "safe to automate". The plain `ost-agent lanes` prints `unclassified N`, `Runnable right now (compute-only, no result yet): N`, per-test `⚠ likely humans-required` hints, and with `--runnable` a bare scriptable list; **nothing in the spec asserts a `proseDeclared` section**, so the 113 are not something a shipped command is pinned to print — though that is an absence from a spec rather than from the code, and is the weaker half.

So two framings this node used to carry were wrong in the same direction. It is neither "a permission decision, the operator's alone" nor "a build of one predicate": it is a command that already ships. The operator's cheapest move is to type `ost-agent lanes --flag-cautious <their name>` and read what it flagged.

**The residual trap on that recommendation.** `--by` is a free string — one test in that very spec invokes `cli(["lanes", "--vault", dir, "--flag-cautious", "loop"])`, so the by-value can be any text, including a loop's name. "Human-set" is only as true as that string. The command's authority comes from a person choosing to run it, not from anything the record can prove afterwards, and whoever builds the audit candidate has to decide what it does with a `--by` it cannot verify.

**And the yield problem, which qualifies the recommendation rather than withdrawing it.** `cautionBacklog` skips any test already carrying a lane and asks `suggestCaution` about the rest; `suggestCaution` matches `title + body` against `PEOPLE_MARKERS`, a deliberately narrow literal list — interviews, interviewing, recruit, strangers, participants, cohort, survey, pre-order, willingness to pay, consent, usability, design partners, `real (players|users|operators|teams|customers)`, `outside (teams|operators|people)`. Every one names a person **outside** the building. This tree's humans-required population is overwhelmingly about people *inside* it — the operator, the founder, "someone with the build loop's source open". Over the 48 distinct test titles an unattended surface can see (25 `assumptionWork.needsHumans` + 25 `outstandingAsks`, two shared), **zero carry any marker**: "Ask the operator whether…" does not match because the marker requires "real operators" or "outside operators", and "A human re-judges…" and "A person reads ten compacted bodies…" match nothing at all. The heuristic is not weak here; it is aimed at a different population than this vault accumulated.

**The near-miss makes it concrete and it is one word wide.** Three humans-required tests read in full — "A person reads ten compacted bodies and marks every claim the full body made that the rendering dropped", "Ask the operator whether they'd rather a warning let the write through than have it hard-blocked", and "Ask the founder whether a machine-cleared permit may start a build with nobody watching" — come from different sources and dates and all three end with the identical server-written sentence `humansRequired:` emits: **"A person outside the building is the measurement here: …"**. The marker is `/\boutside (?:teams?|operators?|people)\b/i`. "outside the **building**" does not match it. **The one sentence this product writes onto a test to mark it humans-required is invisible to the product's own humans-required detector.** The cheap repair is a marker for that boilerplate, which would catch every future `humansRequired:` test by construction. Run the command anyway — it is free, one-way, and cannot reverse a permissive call — but expect a low yield, and do not read `Nothing to flag` as "the backlog is classified".

**Limits on this section.** Read off specs and source, never from a run: `test/cli/lanes.test.ts` and `test/ost/lanes.test.ts` in full, `src/ost/lanes.ts` in full. The command is reported as *specced* to behave this way; nothing was executed. The zero-of-48 count is over **titles only** while `suggestCaution` reads the body too, so it is a lower bound on the marker's reach and not a prediction of output. All three tests quoted for the boilerplate already carry `lane: humans-required`, so `cautionBacklog` would skip them regardless — they evidence the near-miss, not the yield. The `^**Lane: ` pattern misses declarations written without bold markers or not at line start, which `proseDeclaredLane` would still read, so 113 is a floor.
