**The need (operator's voice):** "I'm a working man, husband, and father of three, soon to be four. I prioritize my family, but there's no excuses that build new products. The output from my OST needs to be actionable by me pointing my Claude subscription's token generation power at the problem. I need better bootstrappability from the agent with less involvement from me."

**Why it matters:** This is the first opportunity in this vault sourced from a real operator describing their own binding constraint in actual use. The constraint is structural, not motivational: the current critical path (cold-offer test) budgets ~4 operator-hours; the test backlog assumes a human with afternoons. If solutions are only actionable by a human with hours, this tree steers work that will never happen — for this operator and plausibly for the entire solo-founder segment.

**The honest floor (recorded at birth):** compute cannot absorb four things — the operator's identity in outreach (consent), money, validation authority (the proposer must never dispose), and the goal itself. The need is therefore precisely: human involvement measured in MINUTES at decision-shaped moments, never in hours at work-shaped ones. "Zero" is not on the table; "minutes" is the spec.

**A fifth floor item, added by observation rather than by reasoning (2026-07-25, twice):** **the credential that makes work public.** Publishing is not a decision — nobody is weighing anything, and there is nothing for the operator to judge. It is a one-minute mechanical act that only a credential-holder can perform. The spec "minutes at decision-shaped moments" does not cover it; this is a minute at a *permission*-shaped moment, and a pipeline that hands off decisions cleanly will still stall here. See both observed instances below.

**Rung honesty:** assertion — the operator is also the founder, so this is a claim from inside the building. It carries unusual weight anyway: it is a first-person account of a verifiable constraint (time scarcity), not a theory about other people's needs. First non-founder confirmation would come from any outside operator citing the same constraint.

**Litmus (more than one way?):** yes — compute-runnable test triage, prepared decision dockets, exception-paged autonomous loops, delegation protocols are all distinct answers.

## Observed instance — 2026-07-25 autonomous loop, and exactly where it hit the wall

One unattended run took both products from tree to shipped code with **zero operator minutes**: read both vaults, picked each tree's stated next build, wrote tests first, implemented, ran the suites, and pushed. Concretely — `ost-agent` v0.5.0 (the exit-code/status fix) and `tetrix-game-monorepo` `8e6d50c` (the anonymous-funnel instrument that unblocks four assumption tests). This is the strongest observed evidence yet for this need's central claim: compute can absorb the *work* shape.

**Then it hit the honest floor recorded at this node's birth, precisely where predicted.** `npm publish` needs a credential the loop does not have and should not have (`npm whoami` → `ENEEDAUTH`, no `NPM_TOKEN`). RELEASING.md's alternate path — publish a GitHub Release, which fires the publish workflow — was also unavailable, because the environment's git proxy rejected the tag push, so the tag that workflow keys on never reached the remote. **The release commit is on `main`; the package is not on npm.** Filed as `INBOX:2026-07-25-friction-npm-publish-cannot-complete-in-the-unattended-lo.md`.

**What that implies for the candidates below.** "Weekly ten-minute docket - every pending decision arrives prepared as one yes or no" is built for decisions and would carry the fifth floor item badly — "run `npm publish`" is not a yes/no with evidence behind it. Either the docket grows a distinct *pending permissions* lane (chores, not judgements), or credential-holding steps are pushed out of the loop's path entirely (an automation token in CI, triggered by something compute can reach). A human should pick; the agent should not quietly acquire publish rights, and did not.

## Observed instance — 2026-07-25, second loop of the day: compute ran a lane, on the other product

A second unattended run shipped to both products with **zero operator minutes**, and it is worth recording separately from the first because it produced a different *kind* of evidence.

The first run showed compute can absorb the work shape of *building*. This one showed compute can absorb the work shape of **verifying** — which is the half this node's leading candidate is actually about.

**What happened.** The tetrix tree's standing briefing named its highest-leverage next action as a ~15-minute human task: walk five journeys against a live Postgres, because the funnel instrument's real SQL had never executed. The loop did it without a person: found no Docker daemon, found PostgreSQL 16 server binaries on the box instead, initialised a cluster, applied all 23 migrations, and converted the five-journey hand-walk into `visitorFunnelService.pg.test.ts` — 16 checks against the real database, green, re-run on every `pnpm test`.

**Why that is stronger evidence than "a test was written".** The task was *classified by a previous pass as needing a human*, with a time estimate attached. It did not need one. That is a mislabel in the safe direction — exactly the direction the v0.6.0 lane rules force — and it is the first concrete case of the compute-only lane paying, on a product that is not this one.

It also sharpens what the lane triage is for. The saving is not the fifteen minutes. It is that a hand-walk verifies one afternoon and a test verifies every commit forever; the lane triage's real product is *converting expiring human verification into non-expiring mechanical verification*, and the fifteen minutes is a rounding error next to that.

**The honest limit, recorded so this is not read as more than it is.** No defect was found, so the run produced no news. A verification lane that only ever confirms is cheap to run and worth very little; the case that matters is one where compute finds something and a human has to decide what it means. That case has not happened yet.

**Second confirmation of the fifth floor item, and it is now a pattern rather than an incident.** `npm publish` was again unavailable (`npm whoami` → `ENEEDAUTH`), and the tag push was again rejected by the environment's git proxy — the same two failures, in the same order, in consecutive runs. v0.5.0 and now v0.6.0 both sit on `main` and neither is on the registry. Two releases of unpublished work is no longer a stall, it is a growing backlog behind one credential, and every pass that ships more code makes the eventual publish larger and less reviewable. The choice named above — grow a *pending permissions* lane, or push credential-holding steps out of the loop's path — is now overdue rather than open. The agent has not acquired publish rights and will not.

## What the instrument backlog is actually made of — consolidated census, 2026-08-04 → 2026-08-22

Six passes worked the `solutionsMissingInstruments` bucket expecting a queue of unwritten commands. It is not one, and the finding has now been re-measured enough times to be treated as established rather than re-derived. This section is the consolidation of those six; git holds each pass's original wording.

**The headline.** The counter reports "solutions whose tests are prose only" and treats at least four different states as one: genuinely un-instrumented mechanical work; tests whose measurement is irreducibly a person; tests whose subject has already shipped, so any command written for them passes on arrival; and tests whose threshold names two lanes at once. Only the first is debt. The number therefore cannot reach zero, and a pass pointed at it as if it could is being pointed at the wrong thing.

The ratio is stable across every sample that was large enough to carry one: roughly **25–29% instrumentable, over half irreducibly human**, and it did not improve as samples grew or as samples were deliberately chosen for apparent mechanisability. The 2026-08-22 sample of 10 found nothing instrumentable at all, which is what the trend predicts once the mechanical seam is worked out.

**The four shapes, and the different remedy each wants.**

1. **A person's judgement over records already held.** Blind-rating a model's reading, marking a near-miss suggestion correct or misleading, reading a migration diff for changed meaning, ranking past questions by consequence with hindsight, scoring degraded-pass reports where the node explicitly bars the authoring agent from judging. Cheap and retrospective, but the measurement is a reader. No spec substitutes for one. *"Show readers a degraded run report and see whether they notice"* states it outright: "The measurement is what a human notices. There is no mechanical proxy for it, and constructing one would answer a different question."
2. **Compute-runnable analysis that is still not a spec.** *"Draft the decision classes from the older half of the stops and test them on the newer half"* says in its own Cost line that "a session with no human present can run it end to end". It is a hold-out classification over transcripts already committed. It wants the `runnable` lane, not an instrument — and no unattended surface can put it there.
3. **A real environment a spec cannot stand up.** *"Check whether a toolless session can even run the tool check"* has to reproduce a scheduled run with the plugin absent; the question is whether the check executes at all in the environment where the thing it checks is missing, and a spec running inside a working suite is the one place that cannot be asked.
4. **A mechanism-shaped solution carrying a belief-shaped test.** *"A spend ceiling per period that stops the loop dead"* is a guard; its only test is "read back four weeks of spend and judge how much bought something worth having". *"A whole-tree ranked ledger that refuses to publish a row without its reason"* is a refusal; its only test is "do written reasons get challenged, or only read". In both, the human study is a good question about whether the thing is *worth having* and touches nothing about whether the mechanism *works*. A builder handed either still has no definition of done, and adding an instrument to the existing test would measure something the test never asked. The version that survives contact: **every solution needs one test whose verdict a machine can reach, and may need a second that only a person can answer.**

**Four traps that have each already cost a pass.**

- **The shipped-behaviour trap.** A command written for behaviour that already exists passes on arrival, looks like progress, and hands a builder a definition of done that was already met. Confirmed on *"Every count states the denominator it was taken over"* (v0.22.0), *"Do the shipped sweeps actually find a planted instance"* (spec `test/eval/planted-instance.test.ts`, v0.20.0), *"Does refusing a newline inside a wiki-link catch breaks nothing else catches"* (shipped as `check` rule `wrapped-wikilink`), *"Sweep both vault histories for writes that landed as undefined or empty"* (run, threshold cleared, shipped v0.18.0), *"Replay the three recorded failed runs through the journal-alert rule on paper"* (live in `src/runner/journal.ts`), and *"Test can a full pass be done with no delete or edit tool"* (answered by the arrival of `ost_edit_node` and `ost_merge_nodes`).
- **The lane-default trap.** `needsHumans` is the *default* for an unclassified test, not a judgement anyone made — on 2026-08-04 exactly one of 249 tests carried an explicit `lane:`. A pass read the default as deliberate, concluded the lane data was meaningless, and swapped a good instrument off *"Can riskiest-assumption-tested be judged mechanically"* before catching itself and restoring it; its History records the reversal, and the swap also un-cleared that test's observed red. **Any pass reading `assumptionWork` should treat `needsHumans` as "unclassified" and read the node instead.**
- **The two-lane-threshold trap.** A threshold joining a mechanical clause and a human clause with "and" lets one command go green on arithmetic nobody doubted while the clause the solution lives or dies on stays untouched. Four such tests are on record; *"Have an unattended pass resolve ten seeded merge conflicts and grade every resolution"* is the sharpest (mechanical clause: zero conflict markers, zero broken links — trivially achievable; human clause: 9 of 10 resolutions graded correct — the entire question). *"Apply the escalating message to the five-failure session and check where it would have fired"* and *"Count how many past releases a push-first rule would have blocked"* carry the worked annotations. Splitting them is the fix, and it is not an unattended surface's call.
- **The search-key trap, and its correction.** An early pass concluded the mechanical seam was exhausted because the already-instrumented tests almost all had titles beginning *Count*, *Replay*, *Check*, *Time*, *Audit*, *Census*, *Kill*. That inference was right about what had been done and wrong about what was left. Selecting instead by *a mechanical property of the file* — tests carrying a `threshold:` and no `instrument:` — found a large instrumentable set whose titles begin with no mechanical verb at all: *"Try to load the tools from inside the vault directory at all"*, *"Merge the enabling config into five real project settings files and check nothing was lost"*, *"Resume three handed-off passes from their recorded state and check they continue correctly"*, *"Try to confirm a tool surface without invoking any of it"*. **The tell was never the verb. It was whether the threshold names a state of the world a process can put itself into.** *Ask ten buyers* cannot; *merge into five settings files* can, and the fact that a person would have done it by hand is a statement about who was available, not about what the question is. This revises the size of the instrumentable remainder upward; it does not overturn the majority finding.

**Why the runnable set is empty by construction — three mechanisms that compose.**

1. **Only a human can put a test in the compute lane.** "Triage every assumption test by the human-minutes it actually needs, and let compute run the zero-minute lane" records this as deliberate: the permissive call lives on the CLI, `ost_flag_humans_required` takes no lane argument by design, and unclassified fails closed. Its own build note is explicit — *"nothing here moves a test into compute-only, and nothing can: that call is still a human's, and the runnable set is still empty by construction."* Four releases on that branch have not moved it.
2. **The shrinking call is unavailable to an unattended pass too.** `ost_flag_humans_required` is refused at the *permission* layer on the unattended surface — first recorded against the 2026-08-02 third pass, reconfirmed 2026-08-05 on *"Show readers a degraded run report and see whether they notice"* (as clear a case as the tool's `why` argument will ever get), and again 2026-08-22. So a sweep can neither add to the runnable set nor remove correctly-human work from the un-instrumented count. Both directions are shut, which is why the number only ever grows. The asymmetry is the safe way round by design — the tool only ever removes work from compute's reach — so this is very likely a grant nobody added rather than a decision to withhold it.
3. **`solutionsMissingInstruments` cannot see either fact.** It reports "tests are prose only" and cannot distinguish "nobody has written the command yet" from "no command could exist".

**The bias this creates in what unattended passes produce, which matters more than the miscount.** The only way for a pass to move a human-only solution off the list is to attach a *new* instrumented test beside the human one — which grows the tree, where the correct act would have shrunk the outstanding list without adding a node. Passes have taken the growing option repeatedly because it was the only one available.

**A measurement defect, observed 2026-08-06.** The bucket read 64 before any writes. The pass set an instrument on the only test beneath *"Refusals the tool can prevent become refusals the tool never issues"*, and that solution left the list — confirmed by watching it disappear from the alphabetical window. The pass also created three new solutions: two carrying instrumented tests, one carrying a test created with `humansRequired` because an operator's two-week reading is the measurement. After all of it the bucket still read 64. That is 64 − 1 + 1, and the +1 has to be the humans-required solution, because nothing else entered the tree. **So the bucket appears to count solutions that are correctly humans-required**, which means it cannot reach zero by construction. Not certain, and the gap is stated: the new solution's title sorts into the 39 entries the response does not show, so it was never seen on the list directly. What would settle it: raise the display cap, or read the bucket's own predicate.

**What this means for this need specifically.** Compute-alone actionability was being read as "every test gets a command". It cannot be, and pursuing it that way produces commands that pass while proving nothing — worse than an empty field, because an empty field is visibly empty. The residual number does not measure unwritten commands. It measures **unbought hours**: solutions whose only path to evidence runs through a person doing something, in a tree whose founding premise is that those hours do not exist. That reframes the backlog from a task into a finding — **the tree has generated far more demand for human measurement than the operator can ever supply, and no amount of compute closes the gap.** The honest responses are to prioritise ruthlessly among the human tests rather than treating all of them as owed, or to prefer candidates whose riskiest assumption is feasibility, because those are the ones compute can actually settle.

**What a human could change, in rough order of how much it would buy.**

- Move some tests into `compute-only` with `ost-agent lane --set`. Nothing else unblocks the loop's own premise; until then `runnable: []` is guaranteed and the instrument work has no consumer.
- Let the sweep record a reason-for-no-instrument that the counter honours, so *shipped* and *correctly-human* stop reporting as un-instrumented — i.e. count solutions with no runnable definition of done *and* no humans-required test separately from solutions whose definition of done is legitimately a person. Both numbers are useful; added together they are neither. Several nodes now carry that reason in prose where only a reader can find it.
- Grant `mcp__ost-agent__ost_flag_humans_required` on the unattended surface, or accept that lane-setting is CLI-only and run `ost-agent lane "<test>" --set humans-required` over the backlog, starting with *"Show readers a degraded run report and see whether they notice"*.
- A cheap next measurement that would quantify this node's core claim rather than argue it: partition the remaining bucket by the risk category each test names. If desirability and viability dominate, the claim is measured.

**One limit that bounds every instrument written in the 2026-08-04 passes.** An instrument must be red the day it is written, and that surface could not verify it: reading the product repository was off the unattended path, and `ost-agent verify` — the only thing that can record an observed failure — was not on it either. The six instruments added on 2026-08-04 are all of one safe shape: a spec file that does not exist, for a mechanism the solution's own body says is unbuilt, so `vitest` exits 1 on "No test files found". That is genuinely red, and it is red for the weakest available reason — identically red for any question that could have been written on it. **None of them is a build permit and none should be treated as one until `ost-agent verify` has watched each fail.** Later passes hold repo sight and can do better.

**Setting an instrument does not move a test out of `needsHumans`.** Verified rather than reasoned: all five tests instrumented on 2026-08-04 — *"Add the hook and check whether the commit paths a run actually uses all pass through it"*, *"Audit every consumer of the tree for whether it would honour a retraction flag"*, *"Kill ten runs at random points and check what the journal's last line claims"*, *"Replay the four toolless passes and see whether the check names the right file"*, *"Can a pass tell a human edit from its own, using only git"* — still appeared under `assumptionWork.needsHumans` on the next sweep. That is probably correct, since a permit needs an observed failure, but it means the two counts move independently and neither alone says what is buildable. Four further solutions were cleared on 2026-08-05: `record-replay-sufficiency`, `pass-shape-classifier`, `census-drop-history`, `compute-lane-runner`.

**The same shape as the stranded-evidence backlog.** A queue that cannot be emptied by any action available to a pass, standing under a heading that reads as debt — already recorded on "A Context node type for evidence that is true, useful, and not a customer need". The cheap partial fix is not a new node type but a **triage verb**: some way for a pass to record "this test's question is not spec-shaped, and here is which of the four shapes it is", so the count awaiting a command is separable from the count awaiting a person.

Evidence class for this entire section: a census of this vault's own files, taken by the passes that worked the bucket. Assertion about the artifact, not a measurement of anyone's behaviour. Nothing here was tested and no threshold was met. It should be checked by rereading the bucket rather than believed on the strength of having been written down.
