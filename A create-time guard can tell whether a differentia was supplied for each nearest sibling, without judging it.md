#Assumption #unvalidated #evidence/assertion

**Kind: feasibility.** Stated so it can be false: at the moment an Opportunity is created, the tool can (1) find the nodes that would become its siblings — the parent's existing Opportunity children — (2) require one differentia sentence per sibling, and (3) refuse the write when any is missing, all without reading the sentence for quality. If the sibling set cannot be computed at create time (the parent is the Outcome, or the parent's children are mixed layers), or if requiring the argument breaks the single-call create-and-attach contract, the gate cannot be built as described and the solution falls back to a sweep-time check it was meant to replace.

**Why it is worth a node of its own.** The sibling beneath this solution, "Authors required to state a differentia produce discriminators, not boilerplate", is the usability belief and is rightly human-required. It cannot carry the mechanical question, and a solution resting on two beliefs is not covered by a test against one — this is the split the 2026-08-10 census on "A pass that cannot see the repository cannot set an instrument at all" asked for.

**Read against the repository this pass.** `ost_create_node`'s schema carries no differentia argument, and its hierarchy check (an Opportunity attaches under the Outcome or another Opportunity) inspects the parent's layer, not the parent's other children. So the mechanism is absent, not half-built.
