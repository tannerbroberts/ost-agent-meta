I chose it over both ranked candidates on two grounds:

  This vault has been starved of evidence that is not reasoning, and a defect

- It sits **in the health record itself**, which every other claim this loop

Both ranked candidates are annotated with why they were passed over, so the next

## What I think the actual finding is

`loop step` was **not wrong**. It recorded exactly what the shell handed it, and
no amount of care inside the recorder would have caught this — the shell really
did return 0. That is what makes it interesting rather than a bug report.

The defect is that the tool **accepted a command construction in which a red step
cannot come out red**, which is this project's own definition of a check that is
not a check. It is the fifth instance this tree has met of "a rule reports
success while covering less than it claims," and the second to land in the
instrument rather than the subject — the first being the three defective plants
inside v0.20.0's positive-control test.

Five is not a run of bad luck. I annotated
[[A failed pass reports success, so my automation can't tell]] with the full
list and with a question I deliberately did **not** answer: whether this pattern
deserves its own top-level opportunity. I declined to create one, because the
root outcome is about external returning operators and an internal-quality
branch would not serve it — but that is a judgement a human should make on
purpose rather than inherit from my restraint.

## What I shipped

[[Refuse a proving command whose exit code cannot report failure]] — v0.21.0,
commit `87164d6`, **published and registry-confirmed (`npm view ost-agent
version` → 0.21.0)**.

A shell `-c` script with an unguarded pipeline is refused before the child spawns
and before anything is written, so the laundered step never reaches the record.
Same contract the append-only tools already use: *Nothing was written. Fix the
call and retry.*

**The design decision I spent the most thought on: no override flag.** I
considered `--allow-laundered-exit` and rejected it. A proving command that wants
a laundered exit code is a contradiction, and an escape hatch would be reached
for precisely when it does the most damage — a firing in a hurry, at 3am, with a
pipeline it does not want to think about. `set -o pipefail` is one phrase, it is
the *correct* repair rather than a suppression, and after it the command is
genuinely provable. The refusal message prints it.

**The risk I am most worried about, and it is not the one the guard addresses.**
A guard that refuses too much teaches people to stop wrapping commands in
`loop step` at all — which loses the whole record instead of one step of it, and
is strictly worse than the problem. That is why 15 of the 33 new tests exist only
to pin what must *not* be refused: `||`, pipes inside single and double quotes,
escaped pipes, direct `argv` invocations, non-shell binaries that happen to take
`-c` (`python3 -c "print(1 | 2)"`), shells invoked without `-c`, and anything
already enabling `pipefail`. [[Does the guard catch real laundering without
refusing honest commands]] carries the threshold that would catch me being wrong:
**any** false positive over the next 10 firings means the detector is too broad.

I also gave that test a failing condition in the other direction, which I think
matters more than it looks: **zero refusals across 10 firings is not a pass
either.** It would mean nobody writes pipelines and the guard is dead weight in
the hot path. A test that can only come out "confirmed" or "silent" is the exact
disease this node is about, and it would have been easy to write it that way.

And I wrote down the thing the test genuinely cannot see: someone told to add
`pipefail` might instead drop `loop step` and run the command bare. That
satisfies the guard by escaping it, and it is invisible to `runs.jsonl` by
construction — the step simply never appears. Only a human reading a transcript
would catch it.

**Observed output, not claimed:** 70 test files / 543 tests pass; `tsc` clean;
`npm view ost-agent version` → **0.21.0**.

## Correction, written after sealing

**Sealed `unhealthy`, and every recorded step exited 0.** That is not a
contradiction and it is not a bug: `computeVerdict` requires all four work
phases, and this run has `build`, `decide` and `ost-pass` but **no `sense`**.
I never ran one in this vault.

That is the right verdict and I am leaving it. The sense phase is where a pass
harvests whatever evidence accumulated since the last firing — inbox notes,
friction filings, transcript harvest — and this pass genuinely skipped it. It
went straight from "the sibling vault's firing handed me a defect" to building.
The defect was real and the build was right, but the harvest that might have
surfaced *other* evidence never happened, and a record that called this healthy
would be hiding a step I did not perform.

Worth noting what this means about the two vaults' verdicts today: **both sealed
unhealthy, for opposite reasons.** tetrix-ost because its sense phase ran and
honestly failed (no production numbers obtainable); ost-agent-meta because its
sense phase never ran at all. The first is a blocked pass; the second is an
incomplete one. `runs.jsonl` records them identically as `unhealthy`, which is
the correct conservative collapse but does lose a distinction a reader would
want. Not filing that as a defect — the verdict field has one job and does it —
but it is the kind of thing the next pass might weigh if it touches health
reporting.
