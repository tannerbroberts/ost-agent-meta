## The build, and the part that was actually hard

The node's own text names its failure mode: *"A denominator computed by the same broken
traversal is just as wrong — if the walker never enumerates the em-dashed file at all, M
excludes it and the ratio reads 100%."* The eleventh pass turned that into a build-or-don't
condition: **the denominator must come from an independent source.**

I nearly got this wrong in the obvious way. My first instinct was to write a second walker
alongside `readTree()` and compare — which sounds independent and is not: two walks of the
same directory with the same code share the same blindness, and would have agreed with each
other confidently while dropping the same files.

What I settled on is two instruments, because there are genuinely two different failures:

- **Files the walk SAW and dropped.** Here the *same* walk is the correct source, and a
  separate one would be wrong. Only the counter knows it skipped something and why. So
  `readTree()` is now implemented in terms of `readTreeCensus()` rather than beside it —
  the census measures the real counter, not a lookalike.
- **Files the walk NEVER ENUMERATED.** Invisible from inside it by construction. This is
  the one the condition was about, and it needs `git ls-files -z`: an index maintained by a
  different program through a different code path.

Finding the actual defect took longer than fixing it. `readTree()` had a
`if (typeof type !== "string" || !VALID_LAYERS.includes(...)) continue;` — so a node with a
misspelled `type` was enumerated, silently dropped, and subtracted itself from *every count
in the product* with nothing anywhere reporting it. `Nodes: 240` could have been 244 and
nobody would know.

Second thing I found while in there and fixed: `fs.readFileSync` and `matter()` were
unguarded, so unparseable frontmatter **threw out of `readTree()`** and took every command
down with a stack trace naming no file. One malformed node made the whole vault unreadable.
That is now an `unreadable` entry with the filename in it.

## The positive control, which I nearly skipped

`-z` on `ls-files` is load-bearing: vault filenames contain the quotes and em-dashes that
caused the original failure, and without it git C-quotes them into phantom discrepancies on
exactly the files that matter most. I wrote a test asserting an em-dash filename is seen by
both sources, it passed first time, and I almost moved on.

This project's own standing lesson is that **a rule that has only ever reported success is
indistinguishable from one that cannot report failure**, so I ran the control: removed `-z`,
re-ran, and the em-dash test **failed** — 1 failed / 15 passed. Restored, green again. That
took about a minute and it is the difference between a test I believe and a test I hope
about. Recorded in the changelog.

I also ran it against a real vault rather than only fixtures: a copy of tetrix-ost with a
planted typo'd `type` and one node deleted from disk after being committed. Both were named
correctly — the dropped file with its bad type quoted, the deleted one under "the walk never
saw". That is the run that convinced me.

## What I got wrong mid-pass

My first `loop step` for the build phase ran `bash -c 'set -o pipefail; npx tsc --noEmit
&& npx vitest run | tail -6'` **from the vault directory**, not the repo. `tsc` found no
tsconfig and printed its help text. This is precisely the cwd trap the thirteenth pass
recorded, one pass after it recorded it, and I walked into it anyway.

Worth noting what saved me and what did not. `pipefail` was set — the previous pass's guard
message had trained me into it without my thinking about it, which is a small piece of
evidence for [[Does the guard catch real laundering without refusing honest commands]]. But
`pipefail` is not what caught this; I caught it by reading the output. The step was
re-run correctly with an explicit `cd`, and that second step is the one whose **71 files /
559 tests** are quoted in the briefing.
