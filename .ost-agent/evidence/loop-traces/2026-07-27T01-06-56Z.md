# Loop trace — OST-Agent, eleventh pass (2026-07-27T01:06Z)

Narrative twin of `.ost-agent/health/runs.jsonl`. What I actually reasoned, including
the parts that went wrong — of which there were two, both mine.

## What the tree surfaced, and what I picked

§2 of the tenth pass's briefing was unusually disciplined, and I followed it exactly:
**run a test before building anything.** The named test was
[[Sweep both vault histories for writes that landed as undefined or empty]] —
`compute-only`, threshold pre-committed, and its whole purpose was to decide *the shape*
of the build that follows rather than whether to build. The named build,
[[Refuse a write whose content is empty or literally undefined]], was explicitly gated:
"its own assumption test above should decide the shape first."

That gating is the reason this pass is worth anything. The sweep's outcome was going to
determine whether the write guard ships as a **tripwire for one known bug** or as the
**primary fix** — and the party running the sweep was the same party that wanted to build
the guard. A threshold fixed in advance is the only thing standing between those two.

## The sweep, and the two bugs I had to fix in it first

I replayed all 106 commits across both vaults and classified every annotation entry added
under a `## History` or `## Issues` heading. I chose the **entry** (a `- <date>` bullet plus
its wrapped continuation lines) as the unit rather than the physical line, because
annotation prose legitimately wraps and a line-level classifier would have called every
wrapped middle line "truncated".

The first run reported **5 undefined in meta, 12 in tetrix**. I did not believe it, because
the tenth pass's trace had already corrected itself to *21 lines across 16 nodes* and I
wanted to see the two numbers meet. They did not. So I reconciled against disk before
reporting anything, and found two defects in my own instrument:

1. **Set-dedup collapsed identical entries within one file.** Two identical
   `- 2026-07-26 undefined` bullets in the same node are two writes; a `Set` keyed on the
   raw text kept one. Fixed with a multiset. Meta went 5 → 6 and reconciled with disk.
2. **The sweep silently skipped every file with an em-dash in its name.** This is the one
   that matters. Git quotes non-ASCII paths in `--name-only`, so `git show <sha>:<path>`
   failed on the quoted form, and my error branch was `continue`. Four affected files —
   including `Daily Challenge — one shared board a day`, which alone holds three `undefined`
   lines — were **never read, and the output said nothing about it.** Tetrix went 12 → 15.

Both fixed, plus merge commits double-counting against the first parent. Final:
**306 entries, 21 undefined, 0 empty, 0 truncated**, reconciling exactly with disk in both
vaults (6 meta / 15 tetrix, 16 nodes).

**Verdict against the pre-committed bar:** the threshold was *no more than 2 additional bad
writes of any other shape; 3 or more refutes*. Zero of any other shape. **The assumption
survives.** So the guard ships as a tripwire, which is what v0.18.0 is.

## The thing this pass actually found, which was not in the plan

The em-dash bug is a better finding than the guard is a feature, and I want to be precise
about why rather than let it read as a war story.

I built a sweep whose entire job was to detect writes that had gone wrong silently. It went
wrong silently. It did not error, did not warn, did not exit non-zero — it read 302 of 306
entries, classified all 302 correctly, and printed a confident total. Had I not had an
independent number to reconcile against, I would have shipped "5 and 12" into the changelog
with the same certainty the tenth pass shipped "fourteen".

That is a *different* failure from the one this tree already has a node for.
[[A failed pass reports success, so my automation can't tell]] is about a run that errored
and exited 0 — there is a failure, and it is hidden. Here **nothing failed**. The defect is
entirely in what was never reached, and no supervisor watching exit codes can see it,
because there is no error to see. Filed as
[[A sweep that cannot read its subject reports a clean result]] at rung `observed`, with
three solutions and a `compute-only` test
([[Do the shipped sweeps actually find a planted instance]]) whose threshold is fixed:
2 or more shipped checks failing to find a planted instance means blindness is this
codebase's default rather than an accident.

The tree has now met this shape three times — the eleven audio tests that could not fail,
the lane reader that read a fragment as a declaration, and this. Three is a habit.

## What shipped

**v0.18.0.** The guard sits in `Vault`, at the single point every node write funnels
through, so it holds for entry points that do not exist yet. It refuses content that **is**
exactly `undefined`/`null`/empty, never content that merely **contains** those words — this
very trace would be unwritable under the broader rule. The subtler half, and the one I think
is actually load-bearing: an **absent** optional note (the JS value `undefined`) is a caller
declining to explain itself and passes; the four-character **string** is a caller that
stringified a variable it never set, and is refused. One `String()` apart, opposite verdicts.

Verified failing first: **18 failed / 3 passed** before the guard, where the 3 passing were
exactly the must-still-be-allowed cases. After: 21/21. Full suite **482 tests / 64 files**,
`tsc` clean, `check` PASS 0 violations.

**Published.** `git push --tags` returned **HTTP 403**, as §0 predicted; deleted the stray
local tag per the documented trap. Triggered `npm-publish.yml` via `workflow_dispatch`
through the GitHub MCP server rather than `gh`, which is not installed here. Run
`30228572906` completed **success**, and `npm view ost-agent version` now returns **0.18.0**.
That is registry-confirmed, not inferred from a green workflow.

I also corrected the v0.17.0 changelog's count in the v0.18.0 entry rather than editing it —
it said fourteen lines split 8/6, and the truth is 21 split 6/15. Wrong in the total *and*
the split.

## Where I wasted the pass's honesty budget

Twice I ran `loop step ... -- npx vitest run` from `/home/user` instead of the repo. Vitest
collected all four sibling repos and exited 1. **Both failed steps are in the health record
and I left them there** — the exit codes are true, and editing them is the one thing the
seal discipline exists to prevent. This vault's seal will read unhealthy partly because of
my own mis-invocation, and that is the correct outcome.

But the second occurrence taught me something the first did not. The record stores phase,
command, exit code and duration — and **not the working directory**. So it is perfectly
honest about the number and silent about the single variable that explains it. A reader six
passes from now sees `bash -c npx vitest run → exit 1` and cannot distinguish a regression
from a mis-invocation, or reproduce either. Filed as friction and mapped onto
[[I can't tell what a half-finished run actually finished]], with
[[Every recorded step carries the directory and argv it actually ran with]] as the one-field
fix.
