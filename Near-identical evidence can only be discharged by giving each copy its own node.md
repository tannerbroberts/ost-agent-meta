#Opportunity #unvalidated #evidence/assertion

**The need, from the operator's side.** My highest-volume evidence channel produces many records of one recurring event. The tree offers exactly one way to take a record off the outstanding list, and it costs a node. So I am made to choose between a queue that never empties and a tree that fills with the same claim written eighty-seven times — and the rules I am given forbid the second, which means the first is not a choice at all.

**Measured, not felt.** `ost_next_work` reported **87 unmapped evidence items** this pass. Two came from `friction/` and carry distinct content. The rest are `TRANSCRIPT:` session-friction records, and reading them shows the shape: this node's own source records ten events, six `tool_error` and four `retry`, and four of the six are one sentence — a permission the unattended surface does not hold. Dozens of sibling records say the same thing about different session ids.

**Why it cannot be worked around, verified against the code.** `src/processes/tree.ts` states the relation in its own header: *"evidence is mapped iff some node in the tree cites its id as that node's `source`."* One writer, `ost_create_node`'s `source`, which is a single string in node frontmatter. There is no many-to-one form. The doc comment explains — correctly — why the *persisted* mapped-set was deleted: a reader with no writer was a second answer any actor could forge. Deriving the relation was right. Deriving it from a one-to-one field is what produces this.

The consequence compounds with the channel that feeds it. Session transcripts are generated by the loop itself, so every firing that hits friction manufactures another record that a later firing must either duplicate a node for or leave outstanding forever. The queue grows from being worked.

**Whose problem this is.** Not only this vault's. Any operator who turns on a mechanical channel — transcripts, usage, a webhook — buys a stream where most records restate one fact. Manual inbox notes do not have this property, which is why the tree did not have it for its first fortnight.

**More than one way to address it**, so it is not a solution in disguise: cluster records and map a cluster; let a node cite many sources; let an item be dismissed with a recorded reason; or fix it upstream by having the adapter roll near-identical records into one. Those are genuinely different products with different failure modes.

**What this does not claim.** It is first-party throughout — a count off this tree's own tool output and a read of this product's own source. No outside operator has reported it. Rung is the floor, deliberately: the source is a `TRANSCRIPT:` recording and would carry `observed`, but the recording evidences the agent's tool errors, not this claim about evidence accumulation, and taking the higher rung on that technicality would be exactly the laundering the ladder exists to stop.
