Nothing anywhere records "target X was selected on firing Y and the build did not land." WHY THAT DID NOT PREVENT THE RE-SELECTIONS — and this is the part the node asked for. Re-selection is not a memory failure; it is the designed behaviour of a permit that never expires. `permitFrom` clears a permit for any solution with an instrumented test satisfying `observedRed(t) && !observedGreen(t)`. A red observation is append-only and permanent, so that predicate stays true on every subsequent firing until something turns the instrument green. Meanwhile `testsAwaitingVerification` explicitly skips anything already observed — "A test that has already been observed — red or green — is not here. Re-running a red instrument every hour would burn the suite" — so the loop will never re-run it either. The two rules compose into a standing invitation: a target whose build fails (or is abandoned mid-way) keeps its red, keeps its permit, and is re-offered every firing, indefinitely, with nothing recording that it was already tried. That is a sufficient mechanical explanation for the three re-selections observed on 2026-08-16 and 2026-08-19 without needing any additional defect.
