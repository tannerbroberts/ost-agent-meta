#Solution #unvalidated #evidence/assertion
[[A solution whose every test compute may not run holds nothing a builder could start on today]]

**Variation dimension: who-does-the-work. Position taken: nobody — the step is deleted, not reassigned.**

Add one line to `solutionsMissingInstruments` in `src/eval/buildable.ts`: a Solution whose every resolved test sits in a lane `computeMayRun` refuses is not listed. That is the predicate `testsAwaitingVerification` already applies in the same file, so this borrows a rule rather than inventing one, and the two queues stop disagreeing about whether a lane label means anything.

**Why this position and not another.** The sibling candidates both keep the item in front of somebody — one moves it to the ask queue, one makes the exclusion conditional on who set the lane. This one says the listing was simply wrong: the bucket's stated purpose is solutions that "cannot reach a builder, because everything written about it is prose," and a test in the humans-required lane is not prose that failed to become a command. It is a finished decision about who the measurement belongs to. Nothing needs routing, ageing or re-deciding, so the cheapest correct answer is for the queue to stop saying it.

**Cheapest form.** One `continue` guard beside the two already there, importing `computeMayRun` from `src/knowledge/lanes.ts`, plus a row in the doc comment recording why — in the same voice the `shipped` exclusion is already recorded in, since that paragraph exists precisely because the same defect went unexplained once before. *Amended 2026-09-11:* it is one line in each of **two** functions, plus a refusal string that has to be rewritten rather than guarded. The standing finding below has the site list and what it costs this candidate.

**What it deliberately does not do.** It builds no ask queue, no ageing, no report of what it removed. A reader of the sweep will not learn that these solutions exist at all from this bucket.

**What it gives up, plainly, and this is the sharp cost.** Silence is indistinguishable from correctness. Once excluded, a solution whose lane was set too cautiously — by an agent passing `humansRequired:` at creation because it could not think of a command, which is a real and cheap failure mode — disappears from the one list that would have surfaced it, permanently and with no trace. The sibling that distrusts the bare field is built entirely around that risk; this candidate accepts it in exchange for costing one line. It also does nothing about the tests already waiting on a person: it makes the queue honest, not shorter in any way that gets work done.

**What would make this the wrong pick.** If a meaningful share of the bucket carry `humans-required` because a pass defaulted there rather than because a person judged it, this filter cements those defaults out of sight and the tree quietly loses tests it should have argued about. That is the disqualifying condition, it has now been measured, and the census below reports it at **0 hits across 25 of 25 traced entries**.

**Honest note on how this was ideated.** The sweep asks for one blind ideator per dimension. This surface holds no grant to run independent parallel ideators, so all three candidates under this opportunity were composed in one context by one author — the exact condition the blind-ideation rule exists to prevent. Read them as one author's three answers and discount their apparent distinctness accordingly.

## Standing finding: the fix is two sites, not one

Established 2026-09-11, read first-party, and extended by two spec reads on 2026-09-20. Every census on this node from 2026-08-30 onward located the defect in exactly one function, quoting the original finding that `solutionsMissingInstruments` "applies no lane check at all, while `testsAwaitingVerification` two functions below it in the same file does." That is true and it is not the whole site list.

**The second site.** `permitFrom` — the function `buildPermit` and `buildableSolutions` both route through — filters a solution's tests with `tests.filter((t) => nodeInstrument(t.test))` and applies no lane predicate. When that set is empty it returns a refusal whose text is: "none of the N test(s) under X declares a runnable instrument, so none of them can go red or green. Add an `instrument:` naming one spec file to: ..." followed by every test title, laned or not.

**Why that is worse than a second copy of the same omission.** The refusal does not merely fail to exclude a humans-required solution — it instructs the reader to do the one thing the lane exists to forbid, and names the specific tests to do it to. By this file's own account that instruction cannot be carried out: the comment inside `testsAwaitingVerification`, eight lines below, states that `ost_set_instrument` "refuses to create that combination" and calls its own lane check "the second lock on the same door." So `ost-agent buildable` on an all-cautious solution today prints a next step the write surface would reject — worse than a queue listing something it should not, because a silent over-count sends a pass to re-derive a conclusion while this sends it to attempt a refused call.

**What it costs this candidate, and it is a genuine cost.** The sharpest thing this node has going for it is cheapness. That is now one line in each of two functions, plus a refusal string rewritten rather than guarded — because the honest message for an all-cautious solution is not "add an instrument" with a shorter list, it is that the solution's definition of done belongs to a person and no permit is coming. A rewritten refusal is prose someone has to compose, which is exactly the work this candidate's "nobody — the step is deleted" position claims to avoid. It does not sink the candidate; the siblings inherit the same second site, and one of them (routing to the ask queue) arguably has the better answer for the refusal text, since it already has somewhere to send the reader.

**That `solutionsMissingInstruments` carries exclusion guards at all is now stated by the product's own suite, not only inferred.** Read first-party 2026-09-20 from the header of `test/eval/deferred-permit.test.ts`: "It is the same definedness argument `solutionsMissingInstruments` already makes for the same status in the same file: a solution the tree has retired has no unbuilt behaviour left for a red command to define." ## Method and limits, for the whole census

Counts are of files by frontmatter field, so a test whose lane or instrument was written into prose rather than frontmatter is counted as carrying neither. The 67 counts *tests*, not solutions, so it does not convert directly into bucket entries: several may hang beneath one solution, and some beneath solutions already excluded for other reasons — a limit the arithmetic closure above routes around rather than removes.

**The disjointness limit is closed by the route this section long said it lacked.** The standing caveat was: "The disjointness claim is an arithmetic identity over three counts, not a per-file check that no single file holds both — a file holding both plus a file the `type:` match missed would preserve the totals and break it." On 2026-09-20 that check was run first-party: two multiline `Grep` passes over every `*.md` in this vault, matching within a single file across lines. `^lane:[\s\S]*?^instrument:` returned **0 matches across 0 files**, and the reverse ordering `^instrument:[\s\S]*?^lane:` likewise returned **0 matches across 0 files** — run in both directions on purpose, because frontmatter key order is not guaranteed and a one-directional match would have left exactly the hole it was meant to close. So no file on this tree carries both fields, checked per file rather than inferred from totals, and the `ost_set_instrument` refusal holds at 0 of 515 by direct observation. This removes the first half of the named failure mode only. It does **not** remove the second: a file the `type: AssumptionTest` match missed would still preserve the totals, and nothing there re-counted the corpus. Both greps match on frontmatter field lines, so a lane or instrument written into prose alone is invisible to them exactly as it is to every count on this node, and the 515/381/67 figures assume those two fields appear on no layer other than AssumptionTest, which was not separately verified.

On the traces: the 25 entries were the title-ordered head, and the three tail entries were selected for mechanizability rather than at random, so they bound nothing about the other ~42 beyond removing the claim that the tail is unexaminable. Solution-to-test mapping was confirmed by individual trace for the eight labelled entries, the two commercial entries and the five reasoned entries, and inferred from title correspondence for the rest — that inference is the weakest step, it runs toward *overstating* how many are labelled, and the one mapping error recorded in the census was found in the one place it was checked. The 2026-09-19 tracing establishes each solution's test set as of that date; a test added later would change what bucket presence proves. Whether those four entered the bucket *because* of the missing filter rather than for some unexamined third reason is not established — that still rests on the standing finding's behavioural argument.
