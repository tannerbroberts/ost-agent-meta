#Assumption #unvalidated #evidence/observed

**Desirability.** The solution assumes the missing thing is information. It may be that the information was always available and the operator's problem is attention, in which case adding a section at the top of a report changes where the failure sits without removing it.

Stated so it can be false: an operator who receives, every morning, a list of everything the night could not do, stops reading that list. There is a specific mechanism for this and the tree already names it one bucket over — "Three gates fired correctly in one session and every one of them read as noise first" records three correct signals being read as noise on first sight. A refusals section is a signal of exactly that shape: usually the same four entries, usually not urgent, always at the top. The second week is when it stops working, not the first, which is why a one-morning trial would confirm it falsely.

There is a sharper version of the doubt. The five recorded sessions were denied the same four tools every time. A section reporting that would have been byte-identical five mornings running. A signal that never changes is one an operator is right to stop reading — so if this is built at all it may have to report only *new* refusals, or refusals whose blocked work has grown, and that is a different solution from the one the parent node proposes.

Where it could be true: the denials in the record were not merely unread, they were invisible. The operator had no artefact to skim past. There is a real difference between ignoring a line and never being shown one, and the first two weeks of the first version are the only place to find out which of the two this was.

The feasibility half of this solution is not in doubt and is not what this assumption is about: a denied call arrives at the run as an error it can see and count, which is how the transcript adapter came to hold all fifteen of them in the first place.
